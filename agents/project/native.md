# Native playbook

Read before Capacitor, TLS, Electron, downloads, or native-path work.

- Native or CI-untestable changes need real-device verification before merge. State it in handoff or PR.
- Prefer least-breaking hardening. If a fix necessarily breaks an existing native behavior, document accepted risk.
- Plugin import style, TLS trust, and download paths: Native contract in `AGENTS.project.md`. Additionally, plugins match the `@capacitor/core` major version and get mocks in `tests/setup.ts`.
- Use `hooks/useCapacitorListener` for plugin listeners.
- Native logging (`Log.*`, `NSLog`, `CAPLog.print`) never passes through the Logging contract's sanitizer, which lives on the JS side. Never log a URL handed across the bridge, and never log a media or HTTP error object raw. A heuristic gate in `agents-contracts.test.ts` scans `.swift` and `.java` and demands a `// log-safe:` reason on every hit, including its false positives. Stream and event URLs carry the access token in the query, media3 quotes the failing URL in its message and again in the cause chain, and logcat is readable by anyone with adb (refs #307). Log an error code and a scrubbed message instead.
- Never declare an Android permission ahead of the targetSdk that enforces it. `ACCESS_LOCAL_NETWORK` was declared while targeting API 36, where local network access is implicitly granted through `INTERNET`. The declaration replaced that grant on Android 17 devices with a default-denied `NEARBY_DEVICES` toggle nothing requested, so every LAN server timed out (#350). Declaration and runtime request land together with the bump; the gate is in `src/tests/agents-contracts.test.ts`.
- Never resolve a promise with a `registerPlugin` proxy: the proxy intercepts every property access as a native method call, so `.then` on it is probed as an unimplemented method and the awaiter hangs forever. An async helper resolves with the plugin module's namespace and callers destructure the plugin from it after the await.
- A prebuilt xcframework whose `minos` exceeds the app's `IPHONEOS_DEPLOYMENT_TARGET` kills the app at launch on every OS in the gap, before any of our code runs. llama.cpp publishes its xcframework built for iOS 16.4 while the app targets 16.0, so 2.2.0 crashed on launch for every 16.0-16.3 device (#421). The `minos` mismatch is not itself what terminates: dyld loads the framework anyway and dies binding `cblas_sgemm$NEWLAPACK$ILP64`, an Accelerate symbol that does not exist before 16.4. Weak linking does NOT save this - it tolerates a framework being absent, not a symbol its dependency lacks; a weak-linked build crashed identically. The engine therefore lives in `LlamaBridge.framework`, which the app embeds but never links and loads with `Bundle.load()` behind `#available(iOS 16.4, *)`; a shell-script build phase embeds `llama.framework` without linking it, because Xcode only embeds a package product for the target that links it. Nothing the app links may reference llama - check with `otool -L App.debug.dylib | grep llama`, which must come back empty.
- A new framework target needs `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` set, or `GENERATE_INFOPLIST_FILE` produces an Info.plist with no `CFBundleShortVersionString` / `CFBundleVersion` and App Store Connect rejects the upload (90056/90057). The version-bump guard in `scripts/check-native-version-bump.mjs` flags those lines and makes it tempting to drop them; land them in a `chore:` commit instead. Simulator runs never catch this - check the built `Info.plist` (`PlistBuddy -c "Print :CFBundleShortVersionString"`) in a Release build.
- An `@objc` protocol compiled into two binaries is two distinct protocols to the ObjC runtime: the conformance one image registers is invisible to the other's copy, so `as?` fails even though the class is found and instantiated. A protocol shared across a dynamically loaded boundary needs its own framework that both sides link (`LlamaBridgeInterface`), not the same file in two targets.
- SPM caches are purgeable, and macOS empties them file by file while leaving the directory tree standing. A checkout with no `Package.swift` and a bare clone with no `config` fail resolution, and neither symptom names a cache: the CLI reports a manifest missing under a DerivedData path, Xcode reports `Missing package product 'CapApp-SPM'` and `'LlamaKit'`, which reads like the project lost its own local packages. Both trees have to go, the shared `~/Library/Caches/org.swift.swiftpm` clones and this checkout's `<DerivedData>/App-*/SourcePackages`; purging one alone re-resolves straight back out of the other's remains. `npm run ios:fix-spm` does it, `npm run ios` runs it first (about two seconds when healthy), and it purges only on a corruption signature so a real version conflict still fails fast. Gate: `scripts/__tests__/fix-ios-spm.test.mjs`.
- `npx cap run ios` (so `npm run ios`) builds into its own per-device cache, `app/ios/DerivedData/<udid>`, not Xcode's. After a Capacitor major upgrade that cache still holds the old `Capacitor.framework`, the plugins are recompiled against the new one, and the link fails with `Undefined symbols ... dispatch thunk of Capacitor.*` while the same project builds fine from Xcode. Delete `app/ios/DerivedData/<udid>` and rerun. A deploy that then fails with `ERR_UNKNOWN ... error launching app` is the phone being locked: `xcrun devicectl device process launch` names it (`BSErrorCodeDescription = Locked`).
- iOS evaluates the `(orientation: landscape)` media query against the zoomed visual viewport, so mid-pinch it briefly reports portrait and anything keyed on it flickers (the rotation fullscreen bounced out and back). Read `screen.orientation.type` for the device's orientation and keep the media query as the fallback only (`hooks/useAutoFullscreen.ts`).
- iOS simulator runtimes DO enforce `minos`, and old ones are still downloadable (`xcodebuild -downloadPlatform iOS -buildVersion 16.1`). A launch-time dyld failure on an old OS is reproducible without hardware; do not claim it is device-only. Note this cuts both ways: a strong-linked framework whose `minos` was patched up with `vtool` launched fine on a newer runtime, so patched-binary experiments prove nothing here - install a runtime in the real gap instead.
